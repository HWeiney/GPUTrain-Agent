## 1. 若依、认证与权限

### 问题：训练总览接口是如何做权限控制的？

核心回答：接口使用若依已有的Spring Security认证链，并在方法入口通过 `@PreAuthorize("@ss.hasPermi('train:overview:view')")` 做功能权限判断。权限字符串进入若依的RBAC体系，由用户、角色、菜单权限关联决定是否放行；业务服务不重复解析Token或角色。

项目中的具体实现：`GET /train/overview` 返回统一的 `AjaxResult`，当前提供 `READY` 状态、运行中实验数和在线Runner数。控制器只负责协议适配与授权，统计逻辑留在 `TrainOverviewService`，便于后续替换为数据库聚合。

运行时验证：后端加载核心模块后正常启动；未携带Token请求该接口时进入若依安全链并返回业务码401，没有执行受保护方法。若依当前认证失败响应的HTTP状态仍为200、JSON业务码为401，这是继承框架的协议约定，前端请求拦截器按业务码处理；如果对接标准化网关，可再统一为HTTP 401。

菜单与接口采用两层控制：`gputrain_menu.sql` 只把GPUTrain目录和训练工作台菜单分配给内置管理员角色，前端因此不会向普通用户展示入口；后端仍用 `@PreAuthorize` 独立校验，防止用户绕过菜单直接请求API。SQL连续执行两次后仍只有2条菜单、2条管理员关联、0条其他角色关联。浏览器中管理员可打开三卡片工作台；普通用户 `ry` 的动态路由不包含GPUTrain，直接请求接口返回业务码403。

关键代码与测试位置：

- `backend/ruoyi-train-core/src/main/java/com/ruoyi/train/core/overview/TrainOverviewController.java`
- `backend/ruoyi-train-core/src/main/java/com/ruoyi/train/core/overview/TrainOverviewService.java`
- `backend/ruoyi-train-core/src/test/java/com/ruoyi/train/core/overview/TrainOverviewControllerTest.java`
- `backend/sql/gputrain_menu.sql`
- `frontend/src/views/train/overview/index.vue`

常见追问：

- 为什么不直接判断管理员角色？权限标识比角色名更稳定，同一能力可以分配给多个角色，也便于最小权限授权。
- `@PreAuthorize` 何时生效？必须通过Spring代理调用Bean；直接 `new Controller()` 的单元测试只验证返回协议和注解契约，完整鉴权需要运行时安全链或集成测试验证。
- 功能权限和数据权限有什么区别？当前注解控制“能否访问接口”；“访问哪些用户或项目的数据”属于数据范围控制，尚未在该切片实现，不能混为一谈。

容易答错的点：不要声称加了 `@PreAuthorize` 就完成了数据隔离。它目前只验证权限字符串；实验归属、团队共享范围和管理员跨用户可见性仍需在查询层实现。

### 问题：为什么选择模块化单体，而不是直接使用若依微服务版？

核心回答：当前系统部署在一台共享 GPU 服务器周边，团队规模、请求量和独立扩缩容需求不足以抵消服务拆分带来的注册发现、分布式事务、链路追踪和部署复杂度。项目先在同一 Maven Reactor 内建立清晰模块边界，通过 Java 依赖方向约束职责；当监控采集或 Agent 推理出现独立扩缩容需求时，再沿既有边界拆分。

项目中的具体实现：`ruoyi-train-core`、`ruoyi-train-runner-protocol`、`ruoyi-train-monitor` 和 `ruoyi-train-agent` 是独立 Maven 模块。其中 Runner 协议模块不依赖 Spring，控制面通过 `ruoyi-admin` 聚合业务模块。阶段一只在 core 中实现总览切片，避免空架构引入不需要的中间件。

容易答错的点：模块化单体不是“所有代码随便放在一个服务”。重点是模块职责、依赖方向和可测试接口；也不能声称模块已经能独立部署。

## 2. Runner、Linux用户与进程

本章回答基于阶段二代码及本机自动测试；目标 Linux 机的 `systemd --user`、长进程重启和目录边界验收尚未执行，不能表述为已在 GPU 服务器上线。

### 问题：为什么 Runner 主动连接控制面？

核心回答：每个 Linux 用户自己运行 Java Runner，主动通过 HTTPS 注册、心跳、长轮询领取持久化命令并上报结果。控制面不用登录训练机，也不保存 Linux 密码或 SSH 私钥。`RunnerApiController` 暴露协议接口，`RunnerApplication` 负责客户端循环；`RunnerCommandService` 把命令持久化在 MySQL，Redis 仅用于短期在线标记和 Nonce。

常见追问：控制面暂时不可用时怎么办？Runner 对临时网络故障退避重试；已进入 `RUNNING` 的命令不会仅凭租约超时重新排队。恢复时需对账。

### 问题：有 HMAC 为什么还要 HTTPS？

核心回答：HMAC-SHA256 认证请求来源与完整性，不能隐藏正文中的一次性凭据或业务数据。`RunnerRequestSigner` 对 Runner ID、时间戳、Nonce、方法、路径和原始正文摘要签名；`RunnerRequestVerifier` 校验签名与时钟偏差，并用 Redis `SET NX EX` 拒绝重放。非回环流量必须使用 HTTPS；本地开发例外只允许回环 HTTP。

容易答错的点：HMAC 不是传输加密；时间戳本身也不能替代一次性 Nonce。

### 问题：如何保证注册凭据只消费一次？

核心回答：管理员创建有绑定字段与有效期的一次性凭据。`RunnerEnrollmentService.register` 在事务中条件消费，成功后清除临时密文并创建 Runner 与独立密钥；重复消费返回 `ENROLLMENT_ALREADY_USED`。注册后的密钥由控制面 AES-256-GCM 加密保存，Runner 存在本地权限为 `600` 的独立文件中。

常见追问：管理员创建请求重试怎么办？幂等键与绑定字段共同确认同一次创建；绑定不一致或已消费时不再次发放凭据。

### 问题：重复领取命令会不会启动两个进程？

核心回答：命令保存在 MySQL，领取时增加持久化尝试次数；上报时比较 Runner ID、命令 ID、尝试次数和预期状态。`ProcessStateStore` 以命令 ID 保存本地进程身份，重复启动先查看已有状态。处于 `RUNNING` 的命令不会因租约到期重新领取。核心位置为 `RunnerCommandService`、`RunnerApplication`、`ProcessSupervisor`；相关自动测试覆盖重复创建、租约过期和状态不可逆。

### 问题：如何避免 Shell 注入与目录逃逸？

核心回答：管理 API 接受 `ProcessSpec` 的可执行文件和参数数组，`ProcessPolicy` 校验工作目录真实路径、符号链接、可执行文件白名单与环境变量白名单，`ProcessSupervisor` 用 `ProcessBuilder` 传独立参数，不拼接 Shell 字符串。stdout、stderr 与状态文件位于允许目录的 `.gputrain/` 下。测试覆盖 Shell 元字符仍为单个参数及符号链接逃逸。

容易答错的点：仅检查字符串前缀不足以防符号链接逃逸；`ProcessBuilder` 也不自动证明所有参数安全，需要限制可执行文件和运行目录。

### 问题：Runner 重启后如何识别原进程，防止 PID 复用？

核心回答：`ProcessStateStore` 原子保存命令 ID、PID、进程启动时间、可执行文件和参数摘要。重启后 `ProcessSupervisor.recover` 对比实际 `ProcessHandle` 身份；完全匹配才恢复观察，不匹配返回 `PROCESS_IDENTITY_MISMATCH`，不会停止该 PID。Runner 在继续轮询前通过 `/runner-api/v1/processes/reconcile` 上报快照。`KillMode=process` 的 user service 配置为重启保留子进程提供部署条件，但目标机上的实际表现仍待验收。

### 问题：重复停止和进程已退出如何处理？

核心回答：停止请求在 `RunnerCommandService` 中使用目标命令专属幂等键；Runner 只停止本地记录且身份匹配的进程。已保存终态时返回原状态，身份无法确认时拒绝误杀。对 `UNKNOWN` 的恢复状态不猜测退出码，需对账处理。

## 9. Docker与部署

### 问题：为什么不把所有进程都放进Docker？

核心回答：当前阶段用Docker Compose固化MySQL 8.4和Redis 7.4，让团队成员能够用同一套版本和初始化脚本启动有状态依赖。训练任务未来仍由每个Linux账户下的原生Runner启动，因为它需要保留用户文件权限、conda环境、CUDA工具链和已有训练目录；这是一种按职责划分的混合部署，不是为了使用Docker而容器化所有组件。

项目中的已验证实现：

- `deploy/compose.yaml` 只暴露回环地址上的3307和6380端口，避免开发环境数据库直接暴露到局域网。
- MySQL通过 `backend/sql` 首次初始化若依表；数据分别持久化到 `deploy/data/mysql` 和 `deploy/data/redis`。
- `.env` 被Git忽略，仓库只提交 `.env.example`；Spring的 `local` profile通过环境变量读取数据库密码。
- 后端启动时已实际查询9条系统配置和29条字典数据；调用 `/captchaImage` 返回200并在Redis生成 `captcha_codes:*` 键。
- Logback日志目录从硬编码的Linux路径改为 `${LOG_PATH:-./logs}`，并用测试保证跨平台配置不会回退。

关键代码与测试位置：

- `deploy/compose.yaml`
- `backend/ruoyi-admin/src/main/resources/application-local.yml`
- `backend/ruoyi-admin/src/main/resources/logback.xml`
- `backend/ruoyi-admin/src/test/java/com/ruoyi/LocalApplicationConfigurationTest.java`
- `backend/ruoyi-admin/src/test/java/com/ruoyi/LogbackConfigurationTest.java`

常见追问：

- 为什么端口映射到127.0.0.1？开发依赖只供本机访问，缩小攻击面。
- 为什么密码不提供默认值？缺少密码时让应用快速失败，避免误用仓库中的弱口令。
- 为什么MySQL和Redis需要健康检查？容器“正在运行”不等于服务已经能接受请求，后续控制面启动可以基于健康状态编排。
- Bind mount与named volume如何取舍？当前目录挂载便于开发者观察和清理数据；生产环境应使用受管卷、备份和权限策略。

容易答错的点：不要说“用了Docker就能保证所有环境完全一致”。Compose只固定了容器化依赖；宿主机内核、JDK、Node、GPU驱动和原生Runner环境仍需单独约束。Runner 混合部署已有代码和打包材料，目标 Linux 运行验收仍待执行，不能表述为已上线能力。GPU 调度和真实训练执行属于阶段三。

### 问题：数据库已经是 utf8mb4，为什么初始化数据仍然会乱码？

核心回答：服务端、数据库、表、连接和客户端字符集是不同层次。此次 MySQL 8.4 服务端和数据库均为 `utf8mb4`，但容器中的 MySQL 命令行客户端默认是 `latin1`。入口脚本读取 UTF-8 SQL 时先按 latin1 解释，再将错误字符写入 utf8mb4 列，因此数据库合法保存了“双重编码”的错误文本。

定位过程：页面中静态 Vue 文本正常，只有菜单和昵称乱码，先将故障边界缩小到后端动态数据；随后查询 `HEX(menu_name)`，发现“系统管理”存储为以 `C3A7...` 开头的二次编码，而正确 UTF-8 应以 `E7B3BB...` 开头。`SHOW VARIABLES` 进一步确认客户端和连接默认字符集是 latin1。

修复方式：三个初始化 SQL 首行显式执行 `SET NAMES utf8mb4`；Compose 不再挂载无序 SQL 目录，而是映射为 `01-ruoyi.sql`、`02-quartz.sql`、`03-gputrain-menu.sql`，同时解决首次初始化时扩展菜单可能先于建表执行的问题。重建本地数据后再次查询十六进制值验证修复。

关键文件：

- `deploy/compose.yaml`
- `backend/sql/ry_20260417.sql`
- `backend/sql/quartz.sql`
- `backend/sql/gputrain_menu.sql`

常见追问：为什么不能只改浏览器编码？因为错误字节已经作为合法字符串写入数据库，显示层无法可靠还原；应修复导入边界并重新导入可信源数据。
